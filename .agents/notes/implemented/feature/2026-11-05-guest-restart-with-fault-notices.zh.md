# 实例生命周期不可控时重启已绑定设备内的系统

[English](2026-11-05-guest-restart-with-fault-notices.md)

## 问题

已确认的界面故障，即 Android 仍接受命令但输入分发无响应，此前只对管理器能重建已绑定实例的预设做修复。其他预设，包括 `manual.other`、`manual.physical` 和各 AVD 预设，都无法通过重启守卫，只返回一次受控失败。桌面运行时随后进入每三十秒重试的恢复循环，该循环只写日志警告，不会自行改变设备状态。2026-11-04 与 2026-11-05 两次现场中，这一状态分别持续约一小时与八小时，直到用户手动重启 Mower。

这些目标上的已绑定预设不提供自有生命周期。AVD 预设拒绝 `start` 直到用户确认，也拒绝 `stop`，因为实例的生命周期长于 Mower；手动目标则可能由本进程无法重建的启动器拉起。因此守卫表达的是一项真实约束：缺少所有权时，关闭或启动会作用于重建无保证的实例，而既有空闲生命周期规则也禁止用主机级命令替代无主的控制。

用户需要桌面运行时自行修复这一状态，并且需要得知它：一条可能阻塞数小时的修复路径不会产生其他可见状态变化，所以沉默与健康运行无法区分。

## 决策

[设备控制](../../../../docs/subsystems/device-control.md#12-session-lifecycle-devicesession) 拥有重启边界。已确认的界面故障无法使用自有实例生命周期时，会话改用 `adb reboot` 重启已绑定端点内的 Android 系统，而不再返回受控失败。实例、端点身份与 serial 在该重启后仍然存在，因此同一个 Instance Binding 会回来，且不需要管理器所有权。守卫仍然拒绝变化或无法解析的绑定：无法解析到单一 serial 的端点保留受控失败，因为此处的系统重启无法确定作用于哪台设备。

`ProductionSessionADB.reboot` 执行该命令；`DeviceSession._restart_in_device` 拥有调用顺序。失败记录只允许一次系统重启，与既有的单次关闭规则一致，因此同一 Recovery Budget 内的重复恢复调用只会等待就绪，不会再次发命令。ADB 端口不提供重启方法的会话保留受控失败，从而保持既有的替换后端边界。

桌面运行时拥有这一对通知。`_notify_ui_fault` 在修复开始前发送一封 ERROR 通知，因为该修复可能长时间阻塞而不产生任何其他可见状态变化。其后十分钟内的重复故障属于第一封通知开启的那次事件，不再发送故障邮件。`_notify_ui_recovered` 在恢复返回时发送一封配对通知，并要求存在未关闭的故障通知，因此普通重启、停机或没有前置通知的恢复都不发送。通知失败不会阻止修复。两封通知都使用 ERROR 级别，用户已配置的通知级别会放行。

## 考虑过的替代方案

- **保留受控失败并交由用户处理**：这是既有行为。它对缺失的所有权是诚实的，但让无人值守运行长期依赖手动重启，而现场表明用户无法对从未收到的警告作出反应。
- **为 `manual.other` 猜测一个启动器并接管所有权**：该预设指的是用户手动绑定的设备，其管理器身份未知。臆造一个身份会有作用于另一个实例的风险，而 Instance Binding 规则禁止这种做法。
- **执行主机级的模拟器重启命令**：空闲生命周期规则明确禁止用主机级命令替代无主控制，且主机命令可能终止用户在 Mower 之外启动的实例，对实体设备也不可行。
- **每个恢复周期都发送通知**：阻塞的修复会每三十秒重试数小时，按周期发信会让一次事件淹没邮箱。在静默窗口内抑制故障通知、同时仍允许恢复通知关闭事件，可让一次事件等于一对通知。
- **只在恢复成功后才通知**：成功恢复本身无需警告，但阻塞数小时的修复将完全不上报，这正是现场观测到的沉默。

## 后果

手动、实体或 AVD 目标上的已确认界面故障现在会重启已绑定设备内的 Android 系统，并在同一 Recovery Budget 内等待就绪，因此无人值守运行可自行修复，而不是停摆到手动重启。用户每次事件收到一对通知，故障通知在修复前到达，恢复通知关闭该事件。

系统重启会付出 guest 自身的运行时间：正在运行的应用重新启动，游戏由既有就绪路径重新拉起，而非由该重启本身拉起。若输入分发在模拟器层面而非 guest 内损坏，仍需主机侧重启，这仍是用户的操作。静默窗口固定为十分钟；该窗口内真正的新故障不会再发故障邮件，也不会重置已记录的事件时间。恢复本身仍不保证游戏到达可用场景，这由既有识别边界负责。

## 验证

聚焦离线测试通过：[设备恢复监督](../../../../arknights_mower/tests/device_recovery_supervision_tests.py) 覆盖通知配对、静默窗口，以及通知失败后修复仍在运行；[界面恢复](../../../../arknights_mower/tests/device_ui_recovery_tests.py) 通过真实会话顺序覆盖就地系统重启，断言对已绑定 serial 只发一次重启、没有模拟器关闭或启动、设备 owner 不变。合并的设备会话、界面恢复、界面响应、恢复与恢复监督测试共 441 个用例与 28 个子测试通过。改动模块的 Python lint 通过。

这些检查没有在真实设备上执行重启：证据是离线的会话顺序，而不是观测到的模拟器重启。2026-11-04 与 2026-11-05 的现场提供了所报告的条件，其手动重启表明新的 ADB 会话清除了卡住的输入通道，这与系统重启路径一致，但不构成对该路径的证明。
